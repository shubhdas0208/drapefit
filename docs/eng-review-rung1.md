## Runtime (₹0)

| Piece | Choice | Free-tier limit that matters |
|---|---|---|
| Host | Render free web service (webhook mode) | Sleeps after ~15 min idle; disk is ephemeral; 750 instance-hours/month (one service always on fits) |
| Keep-warm | cron-job.org pings `GET /healthz` every 10 min | Free; same tool later triggers `/tasks/followups` |
| Database | Neon free Postgres | Compute scales to zero after idle (~1 s wake on first query); 0.5 GB storage |
| Parser | Sarvam `sarvam-105b`, `reasoning_effort: low`, JSON schema | Uses existing credits; log tokens per call to watch burn |
| Catalog | Shopify Global Catalog MCP | 5 req/s per client, shared by all users; no documented cost |
| Chat | Telegram Bot API | Free |

Render's ephemeral disk means nothing is stored on the box. All state (sessions, results, redirect tokens, events, processed update IDs) lives in Neon.

## Request pipeline

1. `POST /telegram/webhook`: check the `X-Telegram-Bot-Api-Secret-Token` header, insert `update_id` into `processed_updates` (unique). If it is a duplicate, return 200 and stop. Otherwise start an asyncio task and **return 200 at once** (Telegram retries slow webhooks, which would cause duplicate searches).
2. Per-user lock: one in-flight search per Telegram user. A message that arrives during a search gets "Still working on your last request…".
3. Send the ack ("Searching 2 items…") within 1 s and log `request_received`.
4. Parser: Sarvam → JSON → `RequestSpec` (Pydantic). If it fails, retry once. If it fails again, show a fixed help message and log `parse_failed`. A non-empty `ambiguities[]` sends the question and stores a pending spec. The next reply is parsed together with that pending spec.
5. Per item, in parallel and through the shared rate limiter:
   - `search_catalog`: ships_to=IN, ships_from=[IN], context IN/INR, available=true, `limit=30`, price.max = INR cap in paise (the API converts to USD itself; D39 supersedes the USD-conversion plan).
   - Hard filters in code, on the search hit: currency INR, price ≤ cap, colour match (synonym table, then a title/option regex), out-of-scope category drop.
   - Brand cap: at most 3 per seller domain, keeping catalog relevance order.
   - `get_product(selected=[Size, Color])` on survivors **in rank order until 5 pass the size check**, maximum 8 calls per item (D40). Size check = normalised requested size ∈ normalised in-stock variant sizes. An unmapped size label fails closed and logs `size_unmapped`.
6. Build `Option` objects (frozen dataclass) **only from the `get_product` variant**: title, seller, price_inr, size_label, available, image_url, product_url. The renderer accepts only `Option`. The LLM never touches this path.
7. Render each item as soon as it is ready, so a fast item does not wait for a slow one: one `sendMediaGroup` album (images only; an album cannot carry buttons), then one text list with A1..A5 lines. Each link goes through `/r/{token}`. If the album fails (bad image URL), the bot sends the text list alone and logs `album_failed`.
8. Zero results → the failure copy from the design doc. Partial results → show what was found plus the zero-result line for the rest.
9. `GET /r/{token}`: look up the token (random 10+ chars, from `secrets.token_urlsafe`) → stored target URL → log `link_clicked` → 302. An unknown token returns 404. The URL never comes from a query parameter, so this is **not an open redirect**. When tokens are created, the target host must equal the variant's seller domain from the API.

8 modules. `pipeline.py`, `matching.py` and `render.py` are pure, so most tests run offline against the spike fixtures.

## Data model (Neon)

- `sessions(telegram_user_id PK, last_spec jsonb, pending_spec jsonb, updated_at)`
- `results(id, telegram_user_id, label, item_index, option jsonb, created_at)`: the exact `Option` shown, for the grounding audit
- `link_tokens(token PK, telegram_user_id, result_id, target_url, created_at)`
- `events(id bigserial, ts, telegram_user_id, session_id, type, payload jsonb)`: append-only. Types: request_received, parsed, clarify_asked, results_shown, zero_results, link_clicked, parse_failed, size_unmapped, album_failed, error
- `processed_updates(update_id PK, ts)`: pruned after 7 days
- Retention: rows older than 90 days are deleted by `/tasks/followups`; `/delete` removes all rows for the user.

## Failure modes

| Codepath | Realistic failure | Handled | Test | User sees |
|---|---|---|---|---|
| Webhook | Telegram retries during a slow search → duplicate | update_id dedupe + immediate 200 | yes | one reply |
| Render cold start | Pinger misses, first message waits ~45 s | ack after wake; pinger alert email from cron-job.org | manual | slow first reply |
| Render restart mid-search | In-flight asyncio task lost | none (accepted for Rung 1); event log shows request_received without results_shown | no | silence; user resends. **Watch this in the events table.** |
| Sarvam | Timeout / invalid JSON twice | retry once, then help message | yes | "Couldn't read that, try: grey turtleneck M under 2000" |
| Catalog | 429 under 2 concurrent users | shared limiter + Retry-After | yes | slower reply |
| Catalog | Token expires mid-burst | refresh at 50 min behind a lock | yes | nothing |
| USD conversion | Stale `INR_PER_USD` drops items near the cap | 15% headroom, exact INR check in code | yes | fewer options only |
| Size | Store uses "2XL", user says "XXL" | normalisation table | yes | correct match |
| Size | New label ("M (38-40)") not in table | fail closed + `size_unmapped` event | yes | item missing, no wrong size shown |
| Album | Image URL 404 | text-only fallback | yes | list without photos |
| Neon | Cold compute on first query (~1 s) | inside budget | no | nothing |
| Redirect | Unknown or forged token | 404 | yes | "link expired" page |

No critical gaps: the only silent failure (Render restart mid-search) is visible in the event log and accepted for Rung 1.

## Performance

- One request with 2 items = 2 searches + up to 10-16 `get_product` calls. At 5 req/s that is ≥ 2.4-3.6 s of catalog time, plus Sarvam (~2-4 s). One user fits p95 < 8 s. Two concurrent users share the 5 req/s and may reach ~10 s. Per-item streaming hides part of that, because item A arrives before item B finishes.
- The 10-min `get_product` cache (in memory, lost on restart, which is fine) makes "same request again" nearly free.
- Neon queries are single-row lookups or appends.
