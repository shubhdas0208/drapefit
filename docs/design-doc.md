## Problem Statement
A man in Bengaluru wants "a grey turtleneck, size M, and blue bell-bottom pants, waist 32, under ₹2,000 each." Today he opens Myntra, Amazon, and 3-4 D2C brand sites he saw on Instagram. Each has its own filters, and size availability is only visible after clicking into each product. Checkout happens separately on each site. A request with several items, specific attributes, and a price cap per item takes 30-60 minutes across 5+ tabs.

The product is a chat agent. The user types the whole request in one message. The agent shows up to 10 in-stock options per item from Indian Shopify D2C brands. The user adds items to a cart by chatting ("add #3 and #7") and then checks out.

## What Makes This Cool
- One sentence in, a cart out. The whole multi-item, multi-attribute request is parsed at once and split into separate searches.
- Size-aware: only variants that are actually in stock in the requested size are shown. Big marketplaces hide this until you click in.
- It finds D2C brands that are missing from Myntra and Amazon.
- Trust by design: the model never invents a price, size, or stock state. Every number shown comes from the catalog response.

## Constraints
- Solo PM-builder, evenings and weekends. Bengaluru. Sarvam API available (OpenAI-compatible V2).
- Avoid WhatsApp. Use Telegram or a web chat page, so there is no risk of the account being banned.
- Free or near-free APIs only for v1.
- Real users come from colleagues and friends (young professionals, students).
- The agent never handles card or UPI details. Payment always happens on a checkout page owned by the merchant or the payment provider.

## Premises (agreed / adapted)
1. The LLM only translates. It turns NL into a structured spec: items[] with {category, color, size, gender, max_price}. All prices, sizes, and stock values come from catalog API responses. If a field is ambiguous ("size 30" for a turtleneck), the agent asks instead of guessing.
2. The agent never pays. The user approves the cart in chat, then pays on the merchant's checkout (handoff URL) or through a UCP payment handler. Payment credentials never pass through our system.
3. Shopping only. A mutual-fund screener stays as a pivot option, not a design goal.
5. No LLM in the output path. Option lists, prices, sizes and links are rendered by code templates straight from API objects. The LLM only parses input and phrases clarifying questions. Grounding = 100% is then a regression test, not a hope.
6. Checkout is a handoff by default. Indian D2C Shopify stores mostly use third-party checkouts (GoKwik, Shiprocket, Razorpay Magic), which likely break UCP native checkout. Assume handoff for 100% of real merchants until the spike proves otherwise.

## Request schema (Sarvam output, validated with Pydantic, retry once on failure)
```json
{
  "items": [
    {
      "query_terms": "turtleneck",
      "category": "top",
      "color": "grey",
      "size": "M",
      "size_system": "alpha|chest_in|waist_in|unknown",
      "gender": "men",
      "fit": null,
      "quantity": 1,
      "max_price_inr": 2000
    }
  ],
  "budget_type": "each|total",
  "total_max_inr": null,
  "ambiguities": [
    {
      "item_index": 0,
      "field": "size",
      "question": "Size 30 for a turtleneck: chest 30 inches, or XS?"
    }
  ]
}
```
A non-empty `ambiguities[]` means the bot asks before it searches.
4. Free stack: Shopify Global Catalog MCP (API key, no approval), Sarvam for parsing, Telegram Bot API.

## Key facts from research (2026-11-08)
- Shopify Spring '26 Edition: Catalog access needs only an API key. Developers register an agent profile instead of applying for UCP. One Universal Cart feature is still behind an early-access waitlist. Sources: shopify.com/news/spring-26-edition-dev, stellagent.ai summary.
- Global Catalog supports `ships_to` (hard delivery filter) and `ships_from` (merchant origin). `ships_to` defaults to US on the REST endpoint. The REST Catalog search is deprecated in favour of the Catalog MCP. Source: shopify.dev/docs/agents/catalog/global-catalog.
- Currency is a hint. Price filters are denominated in `context.currency`, and businesses convert. There is no India-specific example in the docs. Source: ucp.dev catalog search spec.
- UNVERIFIED (biggest risk): how many Indian D2C merchants are in the Global Catalog with ships_to=IN, how reliable their size/variant data is, and whether any of them support UCP native checkout. Many Indian Shopify stores use third-party checkouts (e.g. GoKwik, Razorpay Magic Checkout, Shiprocket). Those may break native UCP checkout and force a handoff.

## Approaches Considered
### Approach A: Discovery-only gift finder
NL brief, then catalog search, then 3 picks with links to merchant checkout. S effort, medium risk. Rejected by the user as too shallow: no cart and no checkout.
### Approach B: Chat-to-cart with approve-to-buy (CHOSEN)
NL multi-item request, then per-item search, then up to 10 options per item, then cart edits in chat, then the user approves, then checkout. L effort (human ~4-6 weeks / CC ~1 week), high risk because checkout depends on access and merchant support.
### Approach C: Team gift pool
UPI collection plus catalog suggestions plus a group vote. M effort. Deferred.

## Recommended Approach: B, built in 3 rungs so every rung ships to real users

**Rung 1: Search and shortlist (real merchants, real users). Week 1-2.**
- Telegram bot. The user sends a request. Sarvam (`sarvam-105b`, `reasoning_effort: low`, JSON schema output) parses it into items[].
- For each item, call Catalog MCP search with ships_to=IN, ships_from=IN, max_price, and the query terms. Then filter variants in code by size, colour, and availability.
- Hard filters in code apply first: size in stock, INR variant price ≤ cap (re-filter on the returned INR price and drop variants with none), and ships_to=IN. Colour matching uses a synonym table (grey = gray, charcoal, ash, melange, slate) with a title and option-name regex fallback. Size matching uses a normalisation table (S/M/L, chest inches, waist inches).
- Ranking: catalog relevance order, max 3 options per brand for variety.
- Telegram rendering: default 5 options per item and a "More" button, up to 10. For each item, send 1 photo album followed by 1 text list with inline buttons. Options are labelled per item (A1–A5 turtleneck, B1–B5 pants) so "add A3 and B2" is unambiguous. If image-heavy browsing hurts, move to a Telegram Mini App grid (Open Question 3).
- The agent asks a clarifying question on ambiguous sizes (e.g. "size 30" for a top: did you mean 30" chest, XS, or a waist size?).
- State: SQLite (or free Neon Postgres) keyed by telegram_user_id, holding last_spec, last_results, cart and click_outs. This makes "show cheaper" or "same but black" a patch on last_spec plus a re-run.
- Latency budget: acknowledge right away ("searching 2 items…"), process asynchronously, p95 under 8s.
- Click tracking: every outbound link goes through a /r/{id} redirect.

**Failure handling**
| Case | What the user sees |
|---|---|
| 0 results for an item | "No grey turtlenecks in M under ₹2,000 from Indian brands. Try ₹2,500 or charcoal/black?" |
| Results for only some items | Show what was found and the line above for the rest |
| Catalog or Sarvam timeout | "Search is slow right now, retrying…", then one retry, then an apology |
| Out-of-scope item (e.g. electronics) | "I only do fashion for now", and the other items continue |
| Price or stock changed at checkout | Variants are re-fetched before handoff and changes are flagged |

**Rung 2: Cart in chat, checkout by handoff (real merchants).**
- "add 3 and 7", "remove the jeans", "show cheaper", "same but black".
- The cart is grouped by merchant. Items from 2 brands mean 2 checkouts. Multi-merchant Universal Cart is waitlisted.
- On "checkout": build a cart permalink (`https://<store-primary-domain>/cart/<variant_id>:<qty>,...`) per merchant. If the permalink fails, fall back to a product deep link `?variant=<id>`. Send one "Pay on <brand> — ₹X (+ shipping)" button per merchant. The user pays on the merchant's page. UCP checkout sessions get added only if the spike finds a merchant that supports them.
- Measure completion per merchant, not per cart. N merchants means N payments, so expect drop-off after the first.
- Purchase signal: the /r/{id} click-out, then a "did you complete the order?" ping 24h later. The ping is triggered by an external cron (GitHub Actions or cron-job.org) hitting /tasks/followups, because free hosts sleep.
- Privacy: store only the Telegram ID, requests, cart and order answers. Delete after 90 days, and offer /delete on demand.

**Rung 3 (OPTIONAL, timebox 1 weekend, only after the Rung 2 gate): Full in-chat checkout on a store you control (test mode).**
- A free Shopify development store with ~30 seeded products and Shopify's Bogus Gateway only. Razorpay on a dev store may need Indian business setup. Confirm that UCP checkout works on dev stores before committing.
- End to end: cart, in-chat approval against a spend cap ("up to ₹4,000 total, these 2 items"), UCP checkout, a test payment, and an order confirmation in chat.
- This demonstrates the full agentic-commerce loop (consent, mandate, failure handling) without real money, and labels it honestly as a demo.

## Evals (the AI PM core of the project)
- Parse accuracy: 50 hand-written requests (colours, Indian sizing, "under ₹2k each" vs "total", Hinglish). Report per-field accuracy and whole-spec exact match. Matching rules: compare after normalisation (grey = gray, "2k" = 2000), and a null scores correct only when the gold value is null. Target ≥ 90% exact match.
- Grounding check: a regression test that the displayed prices, sizes and stock exactly match the raw API objects. Target 100%, and anything lower fails the build.
- Relevance: human-rated precision@5 per item. Target ≥ 0.7.
- Clarification: the share of cases where the agent should have asked and didn't. Target ≤ 10%.

## Success Criteria
- 5 real users (named colleagues or friends), each with at least 1 real shopping request, within 3 weeks of Rung 1 shipping.
- At least 2 users complete a real purchase from an agent link (Rung 1 product-link click-outs count), confirmed by the 24h follow-up.
- Parse accuracy ≥ 90% and grounding 100% on the eval set.
- Rung 3 demo: a full chat-to-paid-order loop in test mode, recorded.

## Open Questions
1. Catalog coverage for India. This is gating. If fewer than ~30% of test queries return 3 or more relevant in-stock IN-shipping results, pivot: either use a curated list of 20-30 Indian Shopify D2C stores through their public Storefront/products.json, or move to the MF screener track.
2. Does any Indian merchant support UCP native checkout, or is everything a handoff?
3. Can Telegram be skipped for a web chat so images and carousels render better?
4. Size normalisation across brands (S/M/L vs 38/40 vs waist inches) needs a mapping table.

## Spike outcome (2026-11-09)
GO on the Shopify Global Catalog (20/20 queries passed; see `docs/research/spike-01-catalog-20-queries.md`, decisions D15-D18). The curated index fallback is dropped. Retrieval changes: always filter `ships_from=IN`; send the price cap converted to USD (API filters in USD) and keep the exact INR check in code; get each shown product's size/stock matrix with `get_product`, after normalising size labels.

Spike (d) + (e) (2026-11-09): cart permalinks reached Shopify checkout on 7/7 Indian stores (one forces login first); every sampled variant has `native_checkout=false`, so handoff via `/cart/<variant_id>:<qty>,...` is confirmed, with the catalog's `checkout_url` as fallback. Sarvam `sarvam-105b` returned valid schema JSON (user-reported). Channel: Telegram. See `docs/research/spike-02-checkout-and-sarvam.md`, decisions D19-D21.

## Build outcome (2026-11-11)
Rung 1 built in `src/drapefit/` (decisions D37-D45). 167 tests with 96% coverage, including the grounding gate over all 20 spike queries. The live smoke test returns the canonical request ("grey turtleneck M and blue bell-bottoms waist 32, men, under 2,000 each") as 10 in-size options in ~6 s.
- Parser: `sarvam-105b-conversations`, json_object mode. Parse eval: 49/50 on the tuning set, **14/15 held out** (target ≥ 90%), p95 under 0.6 s.
- The catalog price filter accepts INR directly (correction to the spike note).
- Deploy: `docs/deploy.md`. The user creates the accounts (BotFather, Neon, Render, cron-job.org); `scripts/run_local.py` runs the bot on a laptop with only a BotFather token.
